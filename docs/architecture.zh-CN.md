# 目标架构与迁移边界

## Tiger确认的目标

PC仅安装连接客户端；正式网页、模型权重、算法与发布代码统一由4090提供。客户端可以作为独立ZIP由GitHub Releases分发，用户在自己的电脑配置获授权的SSH后使用同一台4090控制AgileX。不是公开一个机器人控制口或共享私钥。

AgileX仍需要设备代理负责真实CAN、相机及本地执行；4090管理其版本和发布。GitHub保存软件版本，原始录制留核验USB，权重留4090；GitHub和PC都不进入50Hz控制循环。现有PC底层源码镜像只保留作历史资料，不再作为新版日常运行或自动发布来源。

## 现有问题

正常重启会改变Boot ID，但当前旧profile同时包含软件SHA、USB挂载设备号和Boot ID，恢复要重写四份相互引用的元数据。软件版本、当前会话、验收记录耦合；反向模型/TimeQP隧道又各自恢复，造成网页起来后V2仍不可用。另有PC与4090的双向工作文件同步，可能把未提交编辑带入生产，PC也直接服务正在编辑的网页目录。仓库目前只有整个历史工作区的空Git，没有可用提交基线。

## 新职责

| 部件 | 职责 | 不拥有的权限 |
|---|---|---|
| PC薄客户端 | SSH身份校验、转发、连接状态、打开服务器页面 | 模型、控制器、相机、CAN、自动重发动作 |
| 4090管理服务 | 统一状态、任务入口、软件版本与发布记录 | 不把页面在线当机器人可执行 |
| 4090推理/规划服务 | 模型生命周期与规划计算 | 未获任务owner不驱动设备 |
| 基础设施恢复器 | 在空闲且身份可验证时恢复登记的通路 | 不自动加载/换模型、清STOP、恢复运动 |
| AgileX设备代理 | 单一CAN/相机owner、反馈、执行和USB记录 | 不接收未准入的候选版本 |
| GitHub/CI | 审查、测试、构建发行包 | 不持生产控制凭据，不连CAN执行测试 |

## 三份独立证据

- SoftwareRelease：版本、commit、组件文件SHA、协议/依赖合同。发布时固定，不包含Boot ID。
- RuntimeSession：真实主机、当前boot、进程身份、实际挂载与端口、owner、真实观察时刻。正常重启后重新建立。
- ValidationRecord：实际检查的路线、模型/检查点、Prompt、软件/会话依赖、结果及范围。保留原件；重启恢复不把旧回执改成新PASS。

新管理层已实现上述状态分开显示；旧控制器的全部依赖与绑定还需逐项迁移，不能现在就删全源码hash或降低USB/STOP守卫。

## 正确的更新过程

1. Codex在4090开发副本或worktree修改，PC客户端开发可在本机独立分支。运行目录不是编辑目录。
2. 保存只影响开发副本，不触发生产同步。用明确提交标记完成的修改。
3. CI执行相关CPU/接口/网页检查，构建带commit和manifest的固定包。
4. 4090下载/缓存已发布版本，校验来源与完整性；GitHub不可达时仍可运行已核验本地版本。
5. 软件启用必须取得唯一部署owner，在锁内复核任务/录制/保存/模型租约，再切版本。现在build/verify/stage已实现，真实控制器activate/rollback协调器仍需接线。
6. 启用失败恢复旧版本并保留失败原因，不恢复运动、不清STOP、不套旧PASS。

推荐先私有仓库审查代码，客户端发行包可单独公开。公共下载只提供连接软件；访问实际设备仍由管理员授予独立SSH身份。

## 首期实际交付与后续

首期交付真实薄客户端、新服务器管理页、兼容旧接口、固定软件包、CPU检查与GitHub CI。不得声称已经完成多用户角色/控制租约、所有底层算法仓库迁移、已签名一键EXE、完整控制器自动激活回滚、速度网络训练或真机验收。后续按这个顺序迁移，不靠删除保护让界面显示就绪。
